**Version:** 1.0

## What PTX is

PTX (Probabilistic Transaction) is a threshold-BLS randomness service running on a
Bitcoin/PIVX-derived PoS chain. A quorum of 11 Gamemaster nodes performs a distributed
key-generation ceremony, then threshold-signs a per-roll seed; the 96-byte aggregated
signature serves as a verifiable random beacon. There are no smart contracts; the protocol
is implemented as special transaction types with consensus validation rules.

## Audit scope

Four items. All are net-new code written in Workstream 1 (W1).

**1. DKG ceremony implementation (five phases)**  
Phase 1 (contribution), Phase 2 (complaint), Phase 3 (justification), Phase 4 (commitment),
Phase 5 (finalize). Scope includes: polynomial share generation over Zr, verification vector
computation and verification, complaint and justification logic, contribution aggregation,
premature commitment aggregation, and the `group_pk` derivation as the sum of valid members'
verification vector free coefficients in G1.

**⚠ Highest-risk item.** A bug in the orchestration — not in the primitives — can produce
a `group_pk` + `sk_share_i` set that signs correctly in isolation but violates the VSS
property: `master_sk` becomes implicitly reconstructable by a party who collected enough
ceremony messages, with no observable signing failure. This is the silent keying-bug class.
Code review will not reliably catch it; it is the primary reason for the external audit.

**2. PTX-key bridge**  
The narrow path from ceremony output to the existing signing path: `sk_share_i` stored in
the same 32-byte `blst_scalar` format; `group_pk` (48-byte compressed G1) wired to
`PTX_BLS_Verify` via the on-chain record for nodes that did not observe the ceremony
directly. The signing path downstream (`PTX_BLS_PartialSign`, `PTX_BLS_Recover`,
`PTX_BLS_Verify`) is unchanged and is not in scope.

**3. PTXDKG special transaction validation**  
After the ceremony, a PTXDKG transaction is mined committing the quorum's `group_pk`,
verification vector hash, member set, and formation height. Validity requires ≥ t valid
signed premature commitments from the named members.

**⚠ Consensus-critical.** Incorrect validation logic — wrong threshold check, wrong member
set validation, wrong `group_pk` aggregation verification — produces a chain split. This
item carries the same review priority as the ceremony itself.

**4. Coordinator-role spec conformance**  
The coordinator's residual post-DKG role is specified as stateless and un-privileged: no
key material held, no trust required for correctness, replaceable by any node with RPC
access to the quorum and the on-chain `group_pk`. The audit should confirm the
implementation matches this spec, including the specific falsifiable requirement: if the
coordinator process is replaced after the ceremony completes, a cold replacement must be
able to initiate roll signing using only the on-chain `group_pk` and quorum member
addresses, with no key-material transfer from the first process.

## Cryptographic substrate

- **BLS12-381** via **blst** (supranational). blst has received its own audit; it is not
  in scope here.
- The ceremony arithmetic (polynomial generation, verification vector computation, share
  encryption, commitment aggregation) is **re-expressed in blst from scratch**, not adapted
  from the existing LLMQ/chiabls path. The LLMQ DKG (`src/llmq/quorums_dkgsession*`) is
  used as a structural reference for phase sequencing and message relay only.
- **chiabls/RELIC is not in the PTX crypto path.** The LLMQ DKG remains in parallel
  for ChainLocks on a separate code path; it does not interact with PTX key material.
- Scheme: NUL-augmentation (no message prepend), custom DST
  `BLS_SIG_HEMIS_PTX_BLS12381G2_XMD:SHA-256_SSWU_RO_NUL_`. Consistent across all PTX BLS
  operations.
- The construction is **Feldman VSS hardened with a GJKR commit-then-reveal phase**
  (KDD-051). Plain Feldman VSS is vulnerable to a rushing-participant bias on `group_pk`:
  because `g^{a_0}` is broadcast in plaintext in Phase 1 before the complaint window closes,
  a member can observe others' free-coefficient commitments and then self-exclude from the
  qualified set (QUAL), biasing the final key. The GJKR commit-then-reveal phase locks QUAL
  before verification vectors are revealed, making `group_pk` unbiasable by ceremony
  participants. The hardening — and any deviation from it — is explicitly within audit scope.

## Scope size estimate

The LLMQ DKG session files (`quorums_dkgsession.cpp/h`, `quorums_dkgsessionhandler.cpp/h`,
`quorums_dkgsessionmgr.cpp/h`) total approximately **2,700 LOC** and provide the closest
structural proxy for the PTX ceremony. The PTX ceremony re-expresses the same five-phase
structure in blst, which we estimate will be similar in scale. Adding the narrow bridge
(~100–200 LOC) and the PTXDKG consensus validation path (comparable to existing PTX special
transaction validators in this codebase, typically 200–400 LOC each), the total net-new
audit surface is approximately **2,000–3,500 LOC**.

This estimate is derived from the LLMQ reference and is indicative only. Definitive scope
sizing will be available at W1.3 handoff.
